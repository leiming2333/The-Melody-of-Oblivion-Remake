# 启动器增量更新

启动器更新优先下载“最近 3 个稳定版本 → 最新版本”的二进制增量补丁；补丁不可用、校验失败、当前版本不在覆盖范围或当前文件不匹配时，自动回退现有的完整包分段下载。

## 协议与安全

- 补丁由 `zig-bsdiff` 生成 TRDIFF10（bsdiff + Zstandard）格式，应用层使用纯 Node 的 `binpatch`，不依赖系统命令、原生工具或 WASM。
- `patch-manifest.json` 绑定 `from`、`to`、平台、架构、安装包名、旧文件 SHA-256、新文件 SHA-256、新文件大小、补丁大小和补丁 SHA-256。
- 启动器先校验清单摘要，再校验当前安装文件确实是清单中的旧版；补丁下载后校验补丁 SHA-256，应用后校验完整目标文件大小和官方 SHA-256。任何一步失败都不会进入安装事务。
- 补丁应用在独立暂存目录完成，当前运行文件不会被原地修改。目标文件与官方发布字节完全一致，因此不会破坏已有代码签名；校验通过后仍走现有的备份、替换、健康确认和回滚流程。
- 补丁清单或补丁文件来自不受信任来源、格式错误、目标大小不符、摘要不符或当前文件已被修改时，直接回退完整下载，不尝试“修复”或跳过校验。

## 覆盖范围与首次升级

支持最近 **3 个已公开稳定版本**。以最新 `v1.9.5` 为例，`v1.9.4`、`v1.9.3`、`v1.9.2` 都可以直接使用增量补丁；更早版本走完整下载。每个发布最多生成 `3 × 8 = 24` 个平台补丁；没有对应旧包或超过体积预算的组合会被跳过。

当前所有用户都在 v1.9.3，尚不认识补丁协议，因此**第一次升级到带补丁功能的版本仍会完整下载一次**。从该版本开始，下一次更新才能使用增量补丁。

清单保留顶层 `from` / `patches` 作为紧邻上一版本的兼容字段，同时用 `sources` 列出最近 3 个来源。已经支持补丁的旧启动器仍能读取顶层字段，新启动器按当前版本从 `sources` 选择。

## 平台差异

- **Windows portable EXE / Linux AppImage**：直接对当前安装文件应用补丁，生成官方新文件。
- **macOS**：安装目录是解压后的 `.app`，不是官方 ZIP。启动器会在用户数据目录保留一份已验证的官方更新 ZIP（约 120 MB），下次对这份 ZIP 打补丁、校验完整 SHA-256 后再用现有 `ditto` 流程解压替换。缓存缺失、损坏或版本不符时回退完整下载；成功后只保留当前版本的基线，旧缓存会被清理。
- **Linux ARMv7**：如果补丁生成或应用环境不满足要求，仍可只走完整下载，不影响其他平台。

## 已做样本验证

用真实 `zig-bsdiff v0.1.26` 对本地 v1.5.5 → v1.5.6 Windows x64 便携包生成 TRDIFF10 补丁：

- 完整包 `89.6 MiB`，补丁 `3.03 MiB`，约 **3.38%**。
- 生成约 14 秒；使用 `binpatch` 还原约 0.6 秒；还原文件 SHA-256 与官方目标一致。

这是历史相邻版本的单机样本，不代表每个版本都保持同样比例，也不能替代 Windows/Linux/macOS 原生安装与启动验收。

## 发布流程

`build.yml` 的 `assemble` 任务在标签构建时：

1. 查找最近 3 个已公开稳定 Release，分别下载八个安装包和 `release-manifest.json`。
2. 下载固定版本 `zig-bsdiff` 并校验 SHA-256（`v0.1.26`，`e417735e3373c6660789216638bd847c7fba49a96d8770968a0b438e6587bd57`）。
3. 对每个旧版本、每个平台生成 `patch-<from>-to-<to>-<target>.patch`，用 `binpatch` 立即还原并核对目标 SHA-256。
4. 超过新包大小 60% 的补丁会被丢弃；全部被丢弃时不发布 `patch-manifest.json`，更新继续走完整包。
5. 生成 `patch-manifest.json` 和 `.sha256`，其中 `sources` 保存 3 个来源，顶层 `patches` 保留紧邻上一版本的兼容条目；随八包一起进入不可变发布目录，由 `publish-release.cjs` 再次校验后上传。
6. R2 同步任务在八包成功上传后，把全部补丁文件与补丁清单上传到 `patches/<tag>/`，逐个回读源站和公开地址校验大小与 SHA-256；失败不会提前切换 `releases/latest.json`。最多 24 个补丁，按每个约完整包 3% 估算约 70–100 MB；实际以发布产物为准。

存在 R2 配置时，补丁和清单同时进入 GitHub Release 与 R2：R2 路径为 `patches/<tag>/<补丁名>` 和 `patches/<tag>/patch-manifest.json`。启动器优先请求 R2 补丁清单和补丁；R2 未配置、缺失、校验失败或不可达时回退 GitHub 与 GitHub 镜像。完整包仍在 `releases/<tag>/`，两套路径互不影响。补丁体积通常只有完整包的几个百分点。

## 验收与排错

```powershell
node --test test/update-patch.test.js test/update-manager-delta.test.js test/release-patches.test.js
npm run check
npm run lint
```

发布前还应：

- 用真实相邻版本生成补丁，记录八个平台的补丁比例、应用耗时和还原 SHA-256。
- 在 Windows、Linux、macOS 原生 runner 上验证补丁安装后的启动、备份和回滚。
- 验证补丁损坏、当前文件被修改、清单摘要错误、补丁下载中断和取消都能回退完整包。
- 验证 macOS 缓存缺失时完整下载，缓存成功后下一次更新使用补丁。
- 检查 Windows 代码签名和杀毒软件不会因最终字节与官方一致而误报。

常见回退原因：没有 `patch-manifest.json`、当前版本不是清单的 `from`、安装文件被修改、补丁超过体积预算、补丁摘要或目标摘要不匹配、网络中断。启动器不会因为增量失败而阻止正常完整更新。

## 已知限制

- 补丁大小取决于构建差异和压缩方式；不能保证每个版本都节省同样比例。
- 覆盖最近 3 个稳定版本；更早版本、草稿/预发布版本或缺少对应旧包时下载完整包。
- 需要保留 macOS 官方 ZIP 缓存才能持续增量；不保留时回退完整下载。
- R2 补丁镜像和完整包共用 `downloads.melodyoblivion.xyz`，但使用独立 `patches/` 前缀；清理旧版本时不要把仍在使用的补丁清单与安装包混在一起处理。
- `binpatch` 为 MIT 许可，补丁格式与 `zig-bsdiff` 的 TRDIFF10 约定需保持兼容；升级工具版本前必须重新跑完整还原测试。
